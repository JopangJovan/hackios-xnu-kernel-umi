# 独立密钥袋事务、重试与普通条目密钥后端

更新：2026-11-20。此目录是用户态实验原型，只处理独立测试目录。
**尚未替换原厂 `keybagd`、系统袋 0 或真实钥匙串，当前 `/private/var` 仍未加密。**
现有锁屏密码与 USB 配对继续使用上一版实现。

## 本轮实现

- `secure_store.c/h`：创建、加载、解锁、锁定、候选改密、提交，以及逻辑 A/C 类条目密钥封装。
- `store-test.c`：全部使用公开测试口令和生成的测试条目；包含进程退出与保存失败注入。
- `build-test.py`：macOS 下编译并运行 ASan/UBSan 检查，保留测试数据供复查；
  `--ios` 只额外编译、签名 arm64 测试程序，不安装、不启动手机。

### 改密与保存恢复

沿用独立 keybag 的 600,000 轮 PBKDF2 和认证密钥封装，改密只重新封装相同主密钥，
因此条目密钥不因密码改变而失效。空密码/关闭密码没有隐式实现，明确拒绝。

状态用固定字节序编码，包含状态序号、密码代次、失败计数、等待时间、实例 UUID、
密码袋及认证标签。每次先写下一组双副本，分别同步，然后原子替换并同步 `commit`。
加载只接受该提交记录指向的精确代次、实例和标签；一个当前副本损坏时可用另一个。
两个当前副本都损坏、提交记录损坏或缺失时，不扫描旧密码袋，也不新建无密码袋。
候选改密单独保存，提交时验证原袋、代次及新袋身份；已提交的旧候选不能再次安装。

写入失败可能发生在 rename 已完成之后，所以接口会清除内存密钥并要求重新打开。
恢复结果可以是已确认的旧状态或新状态，不能将一次 I/O 错误解释为“旧密码一定还有效”。
`fsync` 与进程退出注入验证的是软件恢复流程；没有把它写成真实断电、控制器缓存丢失
或抗恶意整目录回滚的验证。

### 失败重试

先持久化一次尝试计数，再做口令验证；成功也须把计数复位成功，才向调用者释放密钥。
第 3 次失败开始等待 1 秒，随后指数增加，上限 300 秒。拒绝等待期间的尝试；
重新打开时重新履行已保存的等待，进程内时钟倒退不缩短等待。测试用可控单调时钟，
并非通过实际等待几百秒来测试上限；尚未接入原生 UI 的重试提示。

记录认证用调用者注入的 **公开测试策略密钥**。它用于验证协议和恢复逻辑，不能防止
掌握该测试密钥的人修改计数，也不能抵抗恢复整份旧磁盘快照。正式服务需要另行解决
策略密钥来源、权限及回滚边界；不声称具备 Secure Enclave 的硬件防暴力破解能力。

### 普通钥匙串准备

后端采用 AES Key Wrap，并按袋 UUID、存储实例及逻辑保护类分离封装密钥。
测试覆盖改密后恢复同一条目密钥、损坏密文拒绝、保护类替换拒绝、不支持的版本拒绝，
以及 A 类重锁后不可用、C 类首次解锁后可用而重启后重新锁定。

`KB_ITEM_WHEN_UNLOCKED=1` / `KB_ITEM_AFTER_FIRST_UNLOCK=2` 是本实验枚举，
**不是已验证的原厂 AKS keyclass 数值**。版本由调用者明确提供，旧 XOR 包装不进入本后端。
当前 MiniAppleKeyStore 系统袋的 `HKwr`/固定 XOR 路径仍在，不能据此宣称系统钥匙串已加密。
原型由单个所有者串行调用，不是可直接安装的多客户端生产服务。

对照苹果公开的 [SecKeybagSupport.c](https://github.com/apple-oss-distributions/Security/blob/main/keychain/securityd/SecKeybagSupport.c)
确认普通条目经 `aks_wrap_key`/`aks_unwrap_key`，并依赖精确错误语义：锁定/权限错误
被映射为暂时不可访问，解码错误可被视为条目永久损坏。接入时必须区分锁定、服务
暂不可用、格式损坏，不能用统一的解码错误处理未解锁状态，以免影响现有钥匙串。
这是当前公开源码的接口参考，仍须对本机 iOS 16.5 二进制验证 ABI、保护类与返回码。

## 自动检查

```sh
python3 devices/xiaomi-mi-10/experimental/keybag-recovery/build-test.py \
  --output /absolute/path/to/private-test-output --ios
```

脚本新建独立测试目录，不接受真实密码，不读取/修改系统密钥袋或扫描钥匙串。
iOS 程序额外限制目录为 `/private/var/tmp/umi-keybag-recovery-` 加 12 位小写十六进制，
要求有效 UID 0、0700 目录、0600 普通单链接记录；拒绝符号链接与并发写者。
`create` 只允许新目录；`verify` 会读写自己的计数状态，结束后保留供下次重启复查。

主机测试已通过 ASan/UBSan：改密、锁定状态、错误密码、持久重试、损坏记录、
20 个提交保存中断/进程退出检查点、两次后续进程恢复。每次都核对同一组条目密钥，
没有混合密码代次或无密码恢复。保存检查点不等于 20 次物理断电。

真机 `native-67` 完成创建、改密、持久重试与 20 个保存中断/进程退出检查点；
正常回到安卓后，`native-68` 重新加载同一份测试袋，拒绝旧口令、接受新口令，
确认持久失败计数、A/C 生命周期及条目密钥均一致。两轮最终数据卷同步 `errno=0`，
均正常回原厂安卓 `V14.0.4.0.TJBCNXM`。

详见 `results.json`，包含源文件、内核和加载器摘要。临时镜像只替换测试程序和
启动任务，内核及已修复的 USB 加载器源摘要不变。两轮保留固件日志通道，未切换到
原生 USB 配对通道，也没有把它写成又一次配对回归；真实系统密钥袋与配对记录未迁移。
整仓 `prepare.py verify` 仍报告既有 `loader_return.c` 与上游清单不一致，该文件
工作区无修改，最近相关提交为 `4b09a24`；本轮不改写其校验基线。
原始日志仅保存在本地工作目录，不提交系统日志、真实密钥袋或配对材料。

3. 在隔离袋中验证本机普通 AKS ABI、保护类、长度与错误码，先不接管系统袋 0。
4. 明确旧 XOR 条目的版本标记与迁移/拒绝策略、首次解锁前 USB 所需条目生命周期，
   自动检查通过后才替换普通钥匙串路径，并集中回归配对、日志与锁屏。
5. 保持整段 80 GiB 未加密；真实 UFS 数据后端与启动解锁方案另行完成。
